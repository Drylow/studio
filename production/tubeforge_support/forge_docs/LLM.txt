TUBEFORGE PRODUCTION API — VERSION 1

PROJECT IMAGE MODEL MIGRATION (no generation or render is started)
GET /videos/ID/model-migration returns model_snapshot, snapshot_sha256 and
project_provider_exceptions. Changing settings.visuals alone does NOT change
the generation model. Use POST /videos/ID/model-migration with:
{"idempotency_key":"unique-migration-key","expected_snapshot_sha256":"HASH_FROM_GET",
"image_model":"EXACT_CATALOG_ID","image_provider":"cli_proxy",
"acknowledge_untested_model":true}.
The server requires an idle project, validates the current catalog and provider
policy, creates and SHA256-verifies a backup of the full project and media, then
synchronizes model_snapshot and settings.visuals. Existing images and generation
receipts remain unchanged; shots are flagged for regeneration, old reviews become
stale, and an existing render is retained in history. A repeat with the same key
and payload reuses the migration. Conflicting keys or snapshots return 409.
The response contains backup_url for an authenticated ZIP download and its hash.
Provider exceptions are server-configured per project; do not change global policy.
A catalog entry is not a generation test. Generate and inspect ONE shot first.
Review state values are exactly: verified, correct, unreviewed. AI review source
is delegated_ai_inspection. Never mark uninspected images verified.
This migration endpoint does NOT install or expose a RunPod render endpoint.

COMPACT PROMPTS AND RUNPOD RENDERING
GET /videos/ID?fields=id,start,end,prompt&offset=0&limit=10 returns only a page of
shots, prompt_sha256 per row, prompts_sha256 and next_offset. Follow next_offset
until null. Equivalent: GET /videos/ID/scenes/prompts. Limit 1..25.
PATCH /videos/ID/scenes/prompts accepts {"idempotency_key":"edit-001","scenes":[
{"id":22,"expected_prompt_sha256":"HASH_FROM_GET","prompt":"Complete new prompt"}]}.
Optional expected_prompts_sha256 guards the whole list. Up to 25 edits per call;
unknown fields/IDs, duplicate IDs or stale hashes reject the entire call. Same key
and exact payload replay safely. Backups precede edits. Only changed prompts are
replaced: voice, timings, references, existing images/receipts are preserved;
changed shots require regeneration and fresh review. No image call is started.
GET /videos/ID/render/runpod returns configured, ready, blockers and input_sha256.
POST /videos/ID/render/runpod accepts {"idempotency_key":"render-001",
"expected_input_sha256":"HASH_FROM_PREFLIGHT","transition_seconds":0.25,
"intro_fade_seconds":1,"outro_fade_seconds":5}. Returns 202 with job_id,status_url.
Requires verified voice/images, complete timings and no pending regeneration.
Defaults: 1920x1080, 24fps, static camera. RunPod CPU pod, 32 vCPU; never PC/VPS
media processing. Calls create billable RunPod infrastructure. Server credential
is used; do not send provider keys in the body. One pod at a time for this API.
GET /videos/ID/render/runpod/JOB_ID polls durable state. On complete, download_url
is the authenticated MP4 download. Compare video_sha256 and bytes. Pod deletion
is confirmed before completion. Final visual review and publication are separate.
Reconnect with the same key and identical request; do not start duplicate jobs.
POST /videos/ID/render/runpod/JOB_ID/reconcile handles an interrupted controller:
refuses a live controller, deletes its exact pod, marks failure without rerendering.
A new idempotency key is required for an intentional retry after reconciliation.
Generic /actions/render still uses the legacy CPU backend; use /render/runpod.

AUTHENTICATION
Use your own portal member access key, supplied privately by the owner.
POST https://tools.kanye.studio/api/auth with JSON {"accessKey":"YOUR_KEY"}.
Save the kt_session Set-Cookie value. Pass Cookie: kt_session=... OR
Authorization: Bearer SESSION_VALUE on ALL subsequent calls and downloads.
The access key is NOT the Bearer token. Sessions expire after 30 days of
inactivity; log in again on 401. Do not endlessly retry rejected credentials.
Never use/share the owner's session, provider keys or the worker trust token.
All TubeForge members can edit shared presets and team projects. My videos
shows your creations; scope=team exposes existing team productions.

FAST WORKFLOW (explicit asynchronous stages, not a single automatic job)
1. GET /presets. Read the channel's style, voice, character references, scenery
   mode, can_write_script and can_prepare_images. Reuse the saved preset.
2. POST /videos with channel_id, title, script, optional brief/minutes and a
   UNIQUE idempotency_key. Repeating the exact request returns the same video;
   changing its payload with the same key gives 409. Creation never bills media.
   Example: {"channel_id":"CHANNEL_ID_FROM_PRESETS","title":"Alien Invasion:
   30 Days Trapped in an Airport","script":"Your reviewed English narration...",
   "idempotency_key":"airport-episode-01"}. Use a valid single-line JSON title.
3. For an empty script and can_write_script=true: POST
   /videos/ID/actions/write-script with {"minutes":15,"brief":"Story constraints"}.
   Poll /videos/ID/status every 5 seconds. Read/revise the result; do not treat
   the automated writing audit as a human review. Deep Sea and historical
   channels may require an externally written script: capability flags decide.
   Native PUT /api/workspace/projects/ID/script accepts {"text":"..."}.
4. POST /videos/ID/actions/voice with {} uses the saved voice. Wait for completion.
   A completed current voice is reused; {"regenerate":true} explicitly bills a
   new attempt. GET /videos/ID/transcript provides actual word timings (seconds).
   Audio determines duration and shot timing; never generate shots before audio.
5. POST /videos/ID/actions/prepare with {} if can_prepare_images=true. Otherwise
   author shots yourself and save via native PUT /api/workspace/projects/ID/scenes.
   Automatic preparation never replaces an existing shot list. Check narration,
   pacing, characters, locations, viewpoints and reference sources before images.
6. Read GET /videos/ID. Supply missing cast/location/drawing references via the
   native reference upload and location/scene routes. Reference URLs must be
   downloaded using portal authentication. Preserve SHA256 and ordered references.
   Character identity is reused in both free and consistent scenery modes.
   A recurring character needs its own reference. For consistent scenery, import
   inspected location masters/views and the location registry; text alone is not
   proof of consistency. Full project technical_issues explains missing inputs.
7. POST /videos/ID/actions/preview with {} generates the first three shots.
   Download and ACTUALLY inspect all three images. Check 16:9, style, anatomy,
   main-character identity, duplicate characters, scene relevance and references.
   POST /videos/ID/review for EACH inspected scene with {"scope":"scene",
   "scene_id":1,"state":"verified","reviewer":"Colleague AI",
   "source":"delegated_ai_inspection","notes":"Concrete observations..."}.
   Never fabricate inspection notes or call AI review human approval.
8. POST /videos/ID/actions/images with {} generates only remaining missing shots.
   Existing images are kept. Poll status. ACTUALLY inspect every generated image,
   and submit reviews. For individual corrections use native POST
   /api/workspace/projects/ID/scenes/SHOT/generate with confirm_prompt equal to
   the exact saved prompt and image_model/image_provider from model_snapshot.
   Read the native schema and guard responses; do not switch model/provider.
9. Listen/check the audio and its timing; POST /videos/ID/review with scope
   voiceover and honest reviewer/source/notes. Review script separately as needed.
10. POST /videos/ID/actions/render with {}. Existing technical, reference,
   image and voice review checks remain enforced. Render = VPS CPU, native
   FFmpeg, shared render limit. No local clips or rendering fallback.
11. GET /videos/ID/outputs. Download video/voice/shot URLs with auth. MP4 existence
   does NOT mean publication approval. Check final edit/audio before render review.
   publication_ready becomes true only when current evidence and reviews pass.

PRODUCTION QUEUE
POST /queue with {"project_ids":["EXISTING_VIDEO_ID"],"automatic_plans":true}.
GET /queue shows resource usage, limits, job states and next steps.
POST /queue/JOB_ID/cancel stops admission and drains submitted requests.
POST /queue/JOB_ID/resume acknowledges inspected failed/interrupted/changed input.
Queue entries persist on VPS. Separate voice, planning, image and render lanes
avoid blocking another video on missing reviews/authoring. Two image batches
share the configured global image ceiling; one render normally runs at a time.
External native jobs consume capacity too. Existing assets are reused. The queue
parks for preview, image, audio and final inspections; it never invents reviews.
automatic_plans=false waits for authored shots. After restart an active reserved
stage is held as interrupted for inspection rather than replayed automatically.
The website's Video queue page offers Start/Stop/Resume and progress.

NATIVE EXTENDED AUTHORING
Use /endpoints and /openapi.json for every installed endpoint, including shared
channel/preset editing, style/cast uploads, script updates, location registries,
ordered shots, voice overrides, individual image generation and performance limits.
Most native workspace authoring bodies are free-form dictionaries: read the
request contracts in the companion README before writing. Original vendor
endpoints are labeled legacy in the inventory. Never use legacy automatic
run-all/generate paths on authored projects or bypass workspace review checks.
Native API responses may contain root-relative /media or /style-media URLs;
prefix those with /api/2d. Simple project/preset responses do this for you.

FAILURE / RETRY / COST
201=create; 202=stage accepted (not finished); 401=login again; 409=busy/stale/
missing validation or capability; 422=invalid input; 404=not found; 502=upstream.
Status is running, idle, failed or interrupted. idle alone does not mean video
complete: inspect steps, images and outputs. Interruption is not a durable queue;
reconnect, inspect saved artifacts and explicitly resume the missing stage.
No automatic repeated paid generation and no blind POST retry after a timeout:
poll first, inspect artifacts, then decide. Only POST creation is idempotent
by key; generation actions are not exactly-once and may bill a new request.
Already submitted paid provider calls may finish after cancellation.
Respect existing shared concurrency; do not launch unmanaged rendering processes.
Image status counts stored paths; outputs verifies actual files/evidence.
Metadata discovery and fixture tests do not generate paid images/voice.
Uploading references accepts multipart files, max 10 MB per image.
There is no API YouTube publication action in this workflow.

Task recovery and stopping (25 October 2026)
-------------------------------------------
GET /videos/{pid}/operations returns running, operations, stopping, recovery and can_unlock.
Status and project responses also include this execution summary, including individual
shot IDs. Orphaned local states are automatically marked interrupted when no live
owner remains. Files, prompts, reviews and provider receipts are preserved. This never
starts a paid retry or clears an external RunPod reservation.

POST /videos/{pid}/unlock with {} stops new queued work for this project and requests
an orderly stop. It is safe to repeat. unlocked:true means no local task remains;
unlocked:false means drain in progress. Poll operations before retrying. Submitted
image requests finish or hit the execution deadline (default 900 seconds, configurable
by WORKSPACE_IMAGE_TIMEOUT_SECONDS, 60-3600). Provider work may outlive a timeout:
inspect recorded outcomes before deliberately requesting another paid image.
The existing /stop and workspace /images/stop also handle single-image requests.
RunPod running/cleanup_required reservations must use their RunPod reconciliation route.

Different individual shots may run concurrently within the configured provider limit.
The same shot cannot run twice. Structural project edits and rendering still wait for
active image calls. A batch owns its target set until its active calls have drained.

Deployment requirement: run exactly one Uvicorn web worker. Task ownership is in-process; extra web workers cannot safely reconcile each other's tasks. Images still run concurrently through the asynchronous provider queue. The scoped update.sh API deployment pins this setting even when an older Compose override specified multiple workers.
